Users, Permissions & Packages

This lecture explains how Linux identifies users, controls access to files and system resources, delegates administrative privileges, and installs or maintains software packages. These skills are fundamental to secure cloud servers, container hosts, CI/CD runners, web servers, and production Linux systems.

Topic 01

Learning Objectives

At the end of this module, students should be able to perform the following tasks and explain why each task matters in a production Linux environment:

  • Explain the difference between a Linux user account, a group, a UID, and a GID.
  • Interpret the purpose of /etc/passwd, /etc/shadow, /etc/group, and /etc/gshadow.
  • Create, modify, lock, unlock, and remove user accounts safely.
  • Apply least-privilege administration with sudo rather than routinely working as root.
  • Read and change Linux file permissions using both symbolic and octal notation.
  • Manage file ownership and group ownership with chown and chgrp.
  • Explain the purpose of setuid, setgid, the sticky bit, umask, and POSIX ACLs.
  • Install, search, update, and remove packages using common Linux package managers.
  • Apply user, permission, and package-management principles to cloud virtual machines and container images.
Professional focus: The objective is not simply to memorize commands. Students should understand the security model behind the commands so they can make correct administrative decisions.
Topic 02

The Linux Identity Model

Linux is a multi-user operating system. Every process that runs on the system executes under a security identity. That identity determines which files the process can read, which files it can modify, which network ports it can open, and which privileged operations it may perform.

User

A named identity used by a person, service, application, or daemon. Examples include alice, root, www-data, and postgres.

UID

The numeric User ID Linux uses internally. The root account has UID 0. Human accounts commonly receive higher UIDs such as 1000 and above, depending on the distribution.

Group

A collection of identities that can share access to files or resources. Groups reduce the need to assign permissions user by user.

GID

The numeric Group ID used internally by Linux. Each user has a primary group and may belong to multiple supplementary groups.

Inspecting the current identity

Terminal — identity inspection
whoami
id
groups
id username

The whoami command prints the current username. The id command is more complete because it shows the UID, primary GID, and all supplementary groups. The groups command provides a compact view of group membership.

Important distinction: Linux permission checks operate primarily on numeric UIDs and GIDs, not on the visible username text. The names are human-friendly mappings to those numeric identifiers.
Topic 03

Linux Account Database Files

Traditional Linux account information is stored in text-based system databases under /etc. Modern environments may additionally use centralized identity services such as LDAP, Active Directory integration, SSSD, or cloud IAM, but understanding the local files remains essential.

/etc/passwd

This file contains public account metadata. Despite its name, modern systems do not normally store usable password hashes here.

Example /etc/passwd entry
student:x:1001:1001:Cloud Student:/home/student:/bin/bash

The seven colon-separated fields are: username, password placeholder, UID, primary GID, comment/GECOS field, home directory, and login shell.

/etc/shadow

This file stores password hashes and password-aging data. It is intentionally readable only by privileged processes because exposing password hashes would increase the risk of offline password cracking.

Do not edit /etc/shadow manually during normal administration. Use tools such as passwd, chage, usermod, or account-management utilities.

/etc/group and /etc/gshadow

/etc/group defines local groups and their member lists. /etc/gshadow stores protected group administration data.

Safe inspection commands
getent passwd student
getent group developers
getent passwd | head
getent group | head
Why getent is professional practice: It queries the system's configured identity databases through the Name Service Switch. This means it can work with local files and, when configured, external identity sources.
Topic 04

Creating and Managing Users

User administration should follow a lifecycle: create the identity, assign required groups, set authentication controls, verify access, and later lock or remove the account when it is no longer required.

Create a user with a home directory

On many distributions, useradd -m creates the account and its home directory.

sudo useradd -m -s /bin/bash cloudstudent

Set the password

sudo passwd cloudstudent

The administrator sets an initial password without displaying it on screen.

Inspect the account

id cloudstudent
getent passwd cloudstudent
ls -ld /home/cloudstudent

Modify account properties

sudo usermod -c "Cloud Operations Student" cloudstudent
sudo usermod -s /bin/bash cloudstudent

Lock and unlock an account

sudo usermod -L cloudstudent
sudo usermod -U cloudstudent

Account locking is useful for temporary suspension because it preserves files, ownership, and audit history.

Remove an account carefully

sudo userdel cloudstudent
# Remove the account and its home directory only when appropriate:
sudo userdel -r cloudstudent

Password aging

Inspect and configure password aging
sudo chage -l cloudstudent
sudo chage -M 90 -m 1 -W 14 cloudstudent

In the example above, -M 90 sets a maximum password age, -m 1 sets the minimum age, and -W 14 requests a warning period before expiration. Organizational policy should determine the actual values.

Topic 05

Groups and Team-Based Access

Groups are the preferred mechanism for granting shared access to teams. Instead of making several users owners of the same file, the administrator assigns a group to the resource and then adds authorized users to that group.

Create and manage a team group
sudo groupadd devops
sudo usermod -aG devops cloudstudent
sudo usermod -aG devops instructor
getent group devops
id cloudstudent
Important: When using usermod -G, include -a when you intend to append a supplementary group. Omitting -a can replace the user's existing supplementary group list.

Shared project directory

Team directory example
sudo mkdir -p /srv/project-alpha
sudo chown root:devops /srv/project-alpha
sudo chmod 2770 /srv/project-alpha
ls -ld /srv/project-alpha

The 2 in 2770 enables the setgid bit on the directory. New files created inside the directory will normally inherit the directory's group, helping the team maintain consistent group ownership.

Topic 06

sudo, su, and Least Privilege

The root account can perform almost any operation on a Linux system. Because root privileges are extremely powerful, professional administration follows the principle of least privilege: give users only the access necessary for the task and only for as long as necessary.

sudo

Runs a specific command with elevated privileges according to configured policy. It supports per-command authorization and creates a clearer audit trail than simply sharing a root password.

sudo systemctl restart nginx
sudo apt update

su

Switches to another user identity. su - starts a login-style shell. It is useful but should be used carefully because an extended root shell increases the chance of accidental privileged changes.

su - appuser
sudo -i

Editing sudo policy safely

sudo visudo

visudo performs syntax checking before saving the sudoers configuration. This reduces the risk of breaking administrative access because of a malformed policy file.

Example sudoers rule
%devops ALL=(root) /usr/bin/systemctl restart nginx, /usr/bin/systemctl status nginx

This example illustrates restricted delegation: members of the devops group can run only specific service-management commands as root rather than receiving unrestricted root access.

A listing such as -rwxr-xr-- means the owner can read, write, and execute; the group can read and execute; and everyone else can only read.

Topic 08

chmod: Symbolic and Numeric Permissions

The chmod command changes permission bits. Administrators should be comfortable with both symbolic notation and octal notation because both appear frequently in documentation, automation, and infrastructure code.

Symbolic notation

chmod u+x deploy.sh
chmod g+w shared.txt
chmod o-r secrets.txt
chmod u=rw,g=r,o= report.txt

Symbols use u for owner/user, g for group, o for others, and a for all classes. Operators include +, -, and =.

Octal notation

ValuePermissionBinary concept
4read100
2write010
1execute001
7read + write + execute111
6read + write110
5read + execute101
0no permissions000
Common examples
chmod 644 report.txt      # rw-r--r--
chmod 600 private.key     # rw-------
chmod 755 deploy.sh       # rwxr-xr-x
chmod 750 admin-tool      # rwxr-x---
chmod 770 team-directory  # rwxrwx---
Avoid using chmod 777 as a generic fix. It grants write access to everyone and can turn a permission problem into a security problem. Determine the correct owner, group, and required access instead.
Topic 09

Ownership with chown and chgrp

Permissions alone are not enough. Linux also evaluates the file's owner and group to decide which permission triplet applies to a process.

Ownership examples
sudo chown alice report.txt
sudo chgrp developers report.txt
sudo chown alice:developers report.txt
sudo chown -R appuser:appgroup /opt/myapp

The -R option changes ownership recursively. It should be used with caution, especially on system directories. A recursive ownership mistake can make an application fail or weaken system security.

Web server example

sudo chown -R root:www-data /var/www/example
sudo find /var/www/example -type d -exec chmod 750 {} \;
sudo find /var/www/example -type f -exec chmod 640 {} \;

This pattern demonstrates a common idea: directories may need execute/traverse permission while ordinary content files may not need execute permission. The exact ownership and mode must match the web server and deployment architecture.

Topic 10

Special Permission Bits

Linux includes three special permission mechanisms that influence execution or directory behavior: setuid, setgid, and the sticky bit.

setuid — numeric value 4

When applied to an executable in supported circumstances, the process may run with the effective UID of the file owner. Because this changes the privilege boundary, setuid programs require careful security review.

chmod 4755 program

setgid — numeric value 2

On directories, setgid is commonly used for collaborative folders so newly created entries inherit the directory's group.

chmod 2770 /srv/team

Sticky bit — numeric value 1

On a writable shared directory, the sticky bit restricts deletion so users cannot freely remove other users' entries. The classic example is /tmp.

chmod 1777 /shared-temp

Inspect special bits

Use long listings and stat to confirm whether special bits are present.

ls -ld /tmp /srv/team
stat /srv/team
Topic 11

umask: Default Permission Filtering

umask controls which permission bits are removed when a process creates new files and directories. It is not a permission applied after creation; it is a mask that influences the initial mode.

umask
umask -S
umask 027

A umask of 027 commonly results in new files that are accessible to the owner, readable by the group, and inaccessible to others, depending on the program's requested creation mode.

Program requests mode
System applies umask
File/directory is created
Verify with ls -l
Practical lesson: If newly created files are unexpectedly too open or too restrictive, check the user's shell configuration, service unit, application settings, and the effective umask.
Topic 12

POSIX Access Control Lists (ACLs)

Traditional owner/group/others permissions are intentionally simple. When an administrator needs exceptions for individual users or additional groups without redesigning ownership, POSIX ACLs provide more granular access control.

Inspect and set ACL entries
getfacl project.txt
setfacl -m u:alice:rw project.txt
setfacl -m g:auditors:r project.txt
getfacl project.txt
setfacl -x u:alice project.txt

Default ACL for a shared directory

setfacl -m d:g:devops:rwx /srv/project-alpha
getfacl /srv/project-alpha

A default ACL can cause newly created files and subdirectories to inherit specified ACL rules. This is useful for team collaboration but should be documented because ACLs are less obvious than ordinary mode bits.

Troubleshooting clue: A plus sign after a permission string, such as -rw-r-----+, often indicates extended ACL information. Inspect it with getfacl.
Topic 13

Package Management Concepts

Package managers provide a controlled way to install, upgrade, verify, and remove software. Rather than manually copying arbitrary program files into system directories, a package manager tracks metadata, dependencies, versions, repositories, and installed files.

Package

A structured software archive containing program files, metadata, version information, and installation instructions.

Repository

A trusted software source containing packages and signed metadata. Enterprise systems often use internal mirrors or approved repositories.

Dependency

Another package or library required by a program. Package managers resolve dependencies to keep the system consistent.

Package database

Local metadata recording what is installed, the versions present, and which files belong to each package.

High-level package workflow

Refresh metadata
Search / inspect
Install or upgrade
Verify / remove
Topic 14

Debian and Ubuntu Package Management with APT

Debian-based distributions commonly use APT as the high-level package-management interface. Lower-level dpkg tools manage individual .deb packages, while APT handles repositories and dependency resolution.

Refresh package metadata

sudo apt update

This retrieves current repository metadata. It does not by itself upgrade installed packages.

Upgrade installed packages

sudo apt upgrade

Review the planned changes before confirming on important systems.

Search and inspect

apt search nginx
apt show nginx
apt policy nginx

Install and remove

sudo apt install nginx
sudo apt remove nginx
sudo apt purge nginx

Local .deb packages

sudo apt install ./example-package.deb
# Inspect package metadata:
dpkg-deb -I example-package.deb

Using apt install ./package.deb is often preferable to a raw dpkg -i workflow because APT can resolve dependencies from configured repositories.

Topic 15

Fedora, RHEL, Rocky, and AlmaLinux with DNF

DNF is a high-level package manager used by Fedora and modern Red Hat family distributions. It works with RPM packages and repositories.

Common DNF commands
sudo dnf check-update
sudo dnf upgrade
sudo dnf search nginx
dnf info nginx
sudo dnf install nginx
sudo dnf remove nginx
sudo dnf history

dnf history is particularly useful for administrators because it records package transactions and can help determine what changed before a problem appeared.

Topic 17

Updates, Repositories, and Package Security

Package management is part of system security. Unpatched software may contain publicly known vulnerabilities, while untrusted repositories may introduce malicious or incompatible software.

Professional update procedure

  1. Confirm the operating system and repository configuration.
  2. Refresh repository metadata.
  3. Review available updates and security advisories.
  4. Check application compatibility and maintenance windows.
  5. Back up or snapshot critical systems when appropriate.
  6. Apply updates using the distribution's package manager.
  7. Restart affected services or reboot if required.
  8. Verify application health, logs, and monitoring after the change.
Do not blindly copy repository-installation commands from unknown websites. A command that adds a signing key or repository changes the software trust boundary of the machine.

Useful verification commands

# Debian/Ubuntu
apt policy package-name
dpkg -l | grep package-name

# Fedora/RHEL family
dnf info package-name
rpm -q package-name

# General service validation
systemctl status service-name
journalctl -u service-name --since today
Topic 18

Applying These Concepts to Cloud and Containers

Linux users, permissions, and packages are not isolated desktop topics. They directly affect the security and reliability of cloud workloads and containers.

Cloud VM administration

Create named administrator accounts, use SSH keys, restrict sudo privileges, and avoid shared root credentials. Group membership should match job responsibilities.

Service accounts

Applications should run under dedicated identities where possible. A web server, database, and backup agent should not all require unrestricted root privileges.

Container users

Containers often default to root unless the image defines another user. Production images should run as a non-root user when the application does not require root.

Minimal packages

Container images should include only required runtime packages. Fewer packages generally mean a smaller image, fewer dependencies, and a smaller attack surface.

Dockerfile example: non-root application user

FROM debian:stable-slim

RUN apt-get update \
    && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*

RUN groupadd --system app \
    && useradd --system --gid app --home /app app

WORKDIR /app
COPY --chown=app:app . /app

USER app
CMD ["./application"]

The important ideas are: install only what is required, remove package-list cache from the final layer, give the application ownership of only what it needs, and switch to a non-root user before starting the workload.

Why permissions behave differently in bind mounts

When a host directory is mounted into a container, numeric UIDs and GIDs become important. A username inside the container may have the same text as a host user but a different numeric UID. Production container platforms therefore need deliberate UID/GID planning for persistent volumes.

Key security principle: In cloud and container systems, identity, filesystem ownership, process privileges, and package trust form one security chain. A weakness in one area can undermine controls in the others.
Topic 19

Guided Administration Lab

This classroom exercise combines users, groups, permissions, and package management. Perform it only on a training VM or disposable lab system where you are authorized to make administrative changes.

Identify the operating system

cat /etc/os-release
uname -r

Explain which package manager is appropriate for the distribution.

Create a project group

sudo groupadd cloudteam
getent group cloudteam

Create two lab users

sudo useradd -m -s /bin/bash analyst1
sudo useradd -m -s /bin/bash analyst2
sudo passwd analyst1
sudo passwd analyst2

Add both users to the team group

sudo usermod -aG cloudteam analyst1
sudo usermod -aG cloudteam analyst2
id analyst1
id analyst2

Create a controlled shared directory

sudo mkdir -p /srv/cloud-lab
sudo chown root:cloudteam /srv/cloud-lab
sudo chmod 2770 /srv/cloud-lab
ls -ld /srv/cloud-lab

Test access as each user

sudo -u analyst1 touch /srv/cloud-lab/from-analyst1.txt
sudo -u analyst2 touch /srv/cloud-lab/from-analyst2.txt
ls -l /srv/cloud-lab

Observe the group ownership of the newly created files and relate it to the directory's setgid bit.

Install a small diagnostic package

# Debian/Ubuntu example
sudo apt update
sudo apt install tree

# Fedora/RHEL family equivalent
sudo dnf install tree

Verify and then clean up the lab

tree /srv/cloud-lab

# Cleanup only after the instructor verifies the work:
sudo rm -rf /srv/cloud-lab
sudo userdel -r analyst1
sudo userdel -r analyst2
sudo groupdel cloudteam
Instructor discussion: Ask students why 2770 was used instead of 777, why users were placed in a group, and why software installation required administrative privileges.
Topic 20

Troubleshooting Users, Permissions, and Packages

Problem: “Permission denied”

id
namei -l /path/to/problem/file
ls -ld /path /path/to /path/to/problem
ls -l /path/to/problem/file
getfacl /path/to/problem/file

Check the entire path, not only the final file. A parent directory may be missing execute/traverse permission. Also check ACLs, file ownership, service identities, and mandatory security systems such as SELinux or AppArmor when applicable.

Problem: group membership was changed but access still fails

A currently running login session may not immediately gain newly assigned supplementary groups. Start a new login session or use an appropriate session-refresh method, then confirm with id.

Problem: package cannot be found

cat /etc/os-release
# Debian/Ubuntu
sudo apt update
apt search package-name

# Fedora/RHEL family
sudo dnf makecache
dnf search package-name

Verify repository configuration, package name, architecture, operating-system release, and network access to repository mirrors.

Problem: package manager is locked

Do not immediately delete lock files. First determine whether another package-management process is legitimately running. Interrupting an active transaction can corrupt package state.

Topic 22

Review Questions and Discussion

Use these questions for classroom discussion, recitation, or formative assessment.

1. Why is UID 0 special?

UID 0 represents the root superuser identity. Processes running with this identity bypass many ordinary discretionary permission restrictions, so it must be tightly controlled.

2. Why is a group better than chmod 777 for team collaboration?

A group limits access to authorized members, while 777 grants read, write, and execute permissions to every local identity. Group-based access follows least privilege more closely.

3. What is the difference between chmod and chown?

chmod changes permission bits. chown changes the owner and/or group associated with a file or directory.

4. Why should administrators use visudo?

It edits sudo policy with validation and locking support, reducing the risk of saving invalid configuration that could block administrative access.

5. What does sudo apt update do?

It refreshes repository metadata and package indexes. It does not itself install all available upgrades.

6. Why should containers run as non-root when possible?

Running as non-root reduces the privileges available to the application. If the application is compromised, the attacker starts with fewer permissions inside the container and potentially across mounted resources.

7. Why can a file still be inaccessible even when it appears to be readable?

The user may lack execute/traverse permission on one of the parent directories, an ACL may restrict effective permissions, the process may run as another identity, or an additional security system may deny access.

8. What is the professional meaning of least privilege?

Users, processes, and services receive only the permissions required for their legitimate function, with unnecessary privileges removed or constrained.

Closing summary

Linux administration is fundamentally an exercise in controlled trust. Users and groups define identities, permissions define allowed filesystem actions, sudo defines privileged delegation, and package managers define how trusted software enters and changes the system. In cloud and container environments, these controls remain central to secure design.
